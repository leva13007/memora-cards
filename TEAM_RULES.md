# 👥 Team Rules & Guidelines

This document outlines team roles, responsibilities, and communication guidelines for Memora Cards contributors.

---

## 🤝 Team Values

- **Be kind and respectful** — We're all here to learn and build together
- **Be patient** — Especially with newcomers and beginners
- **Assume good intentions** — We're on the same team
- **Ask questions** — No question is too simple
- **Celebrate contributions** — Big or small, all contributions matter

---

## 👨‍💻 Contributor Roles

### Core Contributors

Core contributors have:
- Write access to the repository
- Responsibility for reviewing PRs
- Authority to merge to `develop` and `main` branches
- Commitment to maintaining code quality and project vision

### Regular Contributors

Regular contributors:
- Submit PRs following the git-flow guidelines
- Participate in discussions and code reviews
- Help answer questions from newcomers
- Follow all team guidelines and standards

### Shadow Contributors

Shadow contributors are welcome to:
- Create their own decks locally
- Share feedback via GitHub Discussions
- Learn from the codebase
- Contribute when ready, without pressure

---

## 📋 Responsibilities

### Before Submitting Code

- [ ] Code follows the project's ESLint rules
- [ ] TypeScript types are properly defined
- [ ] Tests pass (if applicable)
- [ ] Documentation is updated (if needed)
- [ ] PR description explains the changes clearly

### Code Review Process

1. **Open a PR** from your feature branch to `develop`
2. **Wait for review** — Core contributors will review within 48 hours
3. **Address feedback** — Make requested changes or discuss alternatives
4. **Get approval** — Once approved, your PR can be merged
5. **Merge** — A core contributor will merge after approval

### Review Guidelines

**For reviewers:**
- Be constructive and specific in feedback
- Explain why changes are needed
- Suggest alternatives when possible
- Approve promptly when ready

**For authors:**
- Respond to feedback promptly
- Ask questions if unclear
- Don't take feedback personally
- Thank reviewers for their time

---

## 💬 Communication Guidelines

### Where to Communicate

- **GitHub Issues**: Bug reports, feature requests, questions
- **GitHub Discussions**: General discussion, ideas, Q&A
- **GitHub PRs**: Code review and technical discussion
- **Discord**: Real-time chat (link in git-flow.md)

### Communication Style

- Use clear, friendly language
- Be specific in bug reports (include steps to reproduce)
- Use emojis sparingly and appropriately
- Keep conversations focused and on-topic

### Response Times

While there are no strict requirements:
- Core contributors aim to respond within 48 hours
- Urgent security issues should be reported immediately
- For questions, community members often help each other

---

## 🔄 Workflow

### Daily Workflow

1. Pull latest `develop` branch
2. Create a feature branch (`feature/MC-{issue}/your-feature`)
3. Make changes and commit following conventional commits
4. Push and open a PR to `develop`
5. Wait for review and iterate
6. Once merged, your changes are in `develop`

### Release Workflow

1. Changes accumulate in `develop`
2. When ready, `develop` is merged to `main`
3. A new GitHub Release is created
4. Version is tagged and documented

---

## 📝 Documentation Standards

- All code should be self-documenting
- Complex logic should include comments
- New features should update relevant docs
- API changes require documentation updates

---

## 🎯 Code Ownership

- No one "owns" specific files — we maintain as a team
- Anyone can suggest improvements to any part of the codebase
- Large refactors should be discussed first via issues/discussions
- Be respectful when suggesting changes to others' code
